Put your organisation's research to work

CorpusKit is an open source research portal. Connect a research collection and people can search it, ask questions that come back with numbered citations, browse the Library and follow the relationships between resources. The evidence stays within reach the whole time, so checking a claim is part of finding it.

An answer you can take apart

A cited answer is a claim with its working attached. Follow one claim from the answer back to the passage that supports it.

Meadows recovered to near their pre-flood extent within three growing seasons, though recovery was slower where winter turbidity stayed above the long-term median 2.

  1. 1Each claim in the answer carries a numbered citation
  2. 2The citation opens the research source behind it
  3. 3The matched passage is marked in the source itself
  4. 4Confidence states, in plain language, how well the sources hold the answer up

It can say no

Not every question has support in a collection, and pretending otherwise is how research tools lose trust. CorpusKit labels weak matches, states low confidence plainly and will answer with nothing rather than a confident guess.

Administrators see the same candour. Knowledge-gap reporting shows what people asked that the collection could not answer, so the gaps become work rather than surprises.

More than one way in

People arrive differently – with a question, a half-remembered report, a topic to browse or a hunch that two things are connected. A portal keeps all of those routes open.

A short cited answer sits above the results by default. Hide it and work with the passages alone, summarise a set of results, or watch a search and hear when its results change.

Ask, as a continuing conversation

Answers stream in with numbered citations, the sources behind them and suggested follow-ups. Answer quality reports relevance, groundedness and context, and confidence is stated in plain language rather than a score alone.

Deep research takes a broad question and maps it into focused sub-questions before answering. Sessions can be saved, renamed and exported, so a line of enquiry can be picked up where it stopped.

A Library of research items, not filenames

Every resource carries a clear title, a summary, key takeaways and notable quotes, whatever the underlying file was called. Search, sort and filter the catalogue, in grid or list view.

A resource page shows the original document, the extracted text, related resources and a conversation limited to that one document, so a question can be put to a single report instead of the whole collection.

A map of what the collection knows

The entity view shows the things the research talks about and the relationships between them. The concept view shows which topics and document kinds occur together.

Search the map, filter it, inspect a connection and open the resources behind it. The map is drawn from the collection, not laid over it, and it reflects the entities and relationships configured for each portal.

Maintained like infrastructure

A research portal earns trust slowly and loses it quickly. Manage treats the collection as something looked after, not loaded once.

Administrators add files, text and webpages, register website sources and schedule synchronisation. Collection health finds what went wrong – failed extractions, bot-challenge pages, resources with almost no text – and drafts stay out of public retrieval until they are ready.

Analysing the collection refreshes its topics, document kinds, suggested questions and the structure of the knowledge map as the research grows, so the portal keeps describing the collection it actually holds.

Read-only access for approved tools

The MCP connector lets an approved external research tool search the collection, request a cited answer, retrieve a document and browse the catalogue. Access is read-only and scoped to one portal.

Access keys are issued by an administrator, shown once and revocable at any time. The credential for the underlying content service never leaves the server.

One deployment, several portals

Each portal has its own name, identity, topics, suggested questions and knowledge-map structure, served from configuration rather than separate branches of the application.

The portals differ where their collections differ. The system underneath stays the same, which is what makes it maintainable.

Run it yourself

The application code is published under the Apache 2.0 licence. Clone it, connect a collection and run the portal on infrastructure you choose and manage.

The repository holds the application, shared types, retrieval integration, tests, build tasks and deployment configuration – the same code that serves the live portals, with documented local setup and container configuration.

One boundary matters when you plan a deployment: content storage and retrieval run on a connected knowledge service, and a deployment needs its own account with one. The Apache 2.0 licence covers the CorpusKit application code; connected services and the research material itself have their own terms.

# clone, configure, run
git clone https://github.com/corpuskit/corpuskit
cd corpuskit
cp .env.example .env   # knowledge service account
deno task dev

local setup and container configuration are documented in the repository

How changes are checked

Every change lands through a pull request. Typechecking, linting, formatting, tests and a full build run on each one, and a red check does not merge. What deploys is what was reviewed.

The same gate applies to maintainers and first-time contributors, which keeps the standard visible instead of implied.

Worth knowing before you commit

  • A deployment needs an account with a connected knowledge service for content storage, retrieval and generation
  • Administrator sign-in supports Microsoft accounts today
  • Application state is kept in SQLite-backed durable storage – simple to operate, and worth understanding before you scale
  • The issue tracker names current gaps and unfinished areas – read it as part of an evaluation

Contributing

CorpusKit is built by developers, designers, researchers and documentation writers working from the same repository that runs the portals. Small contributions are genuinely useful: a careful bug report, a fix with a test, a clearer paragraph of documentation.

Open issues are labelled so you can tell what is ready to pick up, what is under discussion and what remains unfinished. Every change runs the same checks as a maintainer's, and a maintainer reads everything before it lands.
